Security demonstration

Cross-Site Request Forgery (CSRF)

CSRF occurs when a browser with an authenticated session is induced to send an unintended state-changing request. Authentication proves which account made a request; a CSRF token separately helps prove the request came from a form issued by SecureHire.

ATTACK FLOW

How an unintended request can use an authenticated browser

  1. The synthetic buyer is already signed in, so the browser has a SecureHire session.
  2. An unwanted browser submission targets the proposal acceptance action without a valid CSRF token; the missing-token form below represents that request locally.
  3. The server either accepts the fixed fixture action in effectively Vulnerable mode or rejects missing/invalid tokens in Mitigated mode.

MITIGATION

Validate request integrity on the server

In Vulnerable mode, this isolated endpoint observes whether the submitted token is missing, invalid, or valid, then deliberately ignores that result for the one fixed synthetic acceptance action. In Mitigated mode, Flask-WTF validates the token server-side before the action runs; missing and invalid tokens receive HTTP 400 and do not change state.

A CSRF token helps distinguish an intended same-site form submission from an unwanted cross-site request. JavaScript checks are not a substitute because a client can omit or change them. Authentication identifies the browser’s account; it does not prove the account holder intended this action.

The demonstration uses the existing proposal acceptance service only for its dedicated fixture. Normal proposal actions, login, profile edits, Security Lab administration, mode changes, and the reset action remain CSRF-protected in every mode.
