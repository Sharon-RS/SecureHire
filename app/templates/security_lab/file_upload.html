Unrestricted File Upload

In freelance marketplaces, applications frequently accept file uploads such as resumes, portfolio samples, and gig deliverables. Without rigorous server-side validation, attackers can upload server-side scripts (e.g. PHP or Python) to achieve Remote Code Execution (RCE) or HTML/SVG files to trigger Stored Cross-Site Scripting.

ATTACK FLOW

How unvalidated uploads compromise web applications

  1. An attacker locates an upload form intended for benign documents or image attachments.
  2. The attacker crafts an executable server-side script (e.g. a web shell) or disguises a script with an allowed extension.
  3. When validation is missing or naive, the application saves the script with its dangerous extension in a web-accessible directory.
  4. Requesting the uploaded script triggers server-side execution, granting the attacker arbitrary command execution on the host.

MITIGATION

Six pillars of secure file upload architecture

  • Strict Extension Allowlisting: Never use a blocklist. Only allow explicit, required formats (e.g., .pdf, .png, .jpg, .txt) and reject all executable extensions.
  • File Signature (Magic Bytes) Verification: Inspect binary file headers to ensure the file format matches its claimed extension, defeating extension-spoofing attacks (e.g., shell.php.png).
  • File Size Bounds: Cap upload sizes strictly on both client and server to prevent denial-of-service and disk-space exhaustion.
  • Server-Controlled Storage Naming: Never use the user-supplied filename on disk. Generate random UUIDs (e.g. 4f9e...1a.pdf) to neutralize directory traversal and prevent predictable URLs.
  • Storage Outside Web Root: Store files in dedicated private directories (e.g. instance/lab_uploads/) that the web server will not interpret or serve directly as executable scripts.
  • Safe Serving Headers: Serve uploaded files with Content-Disposition: attachment and X-Content-Type-Options: nosniff so the browser treats them as non-executable downloads.
